# Agentic standard

A new agent must find the purpose, authority, current work, implementation and required proof within two links.
AGENTS owns authority. Each fact and each procedure has one owning document.

## Cold context and navigation

README maps the documents. AGENTS owns the repository rules. Start with the operating contract and current
state. Read only the procedure and reference that the next action needs. When a session resumes, read the
changed state. Do not repeat startup.

Measure the complete mandatory reading route, including inherited instructions and required linked reads. Report
the words or estimated tokens and the major duplication. Size helps identify problems. It does not permit the
removal of authority or evidence.

Current docs state the current truth. Replace stale guidance and repair its callers together. Keep history and
fixed receipts outside startup. Link them when needed.

## Skill design

Describe the capability and when to use it. Keep the usual path short: inputs, authority, action, verification,
recovery and exit. Link details for special conditions. Use ordered steps only when the order matters.

- Repair an existing skill before you add one.
- Merge overlapping skills only after you check their callers.
- Keep ordinary commands and decisions outside skills if a wrapper adds no value.
- Prefer existing scripts for repeated fragile mechanics.
- Verify discovery and links. Test an actual task and its failure path. Counts and heading checks do not prove ease of use.

## Execution

Deliver one useful consumer outcome. Define its scope, acceptance criteria and a condition that disproves
success. Keep the full product goal through each useful step. Plan dependencies and ownership. Straightforward
work needs no separate planning artifact.

- Isolate concurrent edits. For solo work, reuse a clean checkout.
- Use existing public interfaces and the setup route of the repository.
- Confirm the source and the prerequisites before you blame the product.
- Group independent reads and compatible changes. Make shared changes one at a time.
- Do not build a second runner, ledger or manager.

## Feedback and capacity

Reduce the elapsed time to the project's full outcome, including verification and integration. Activity, test
counts and running processes are not delivery. Reuse setup and evidence while their exact bindings remain valid.

Delegate separate work only if it saves more than the cost of briefing, review and integration. Name the
outcome, the paths, the proof and the stop boundary. Keep any Owner-required independent review within its
declared scope. Allow the assigned sequence to continue without routine CEO approval. Inspect its result at the
return boundary or a block.

Use the smallest check that separates product, environment and observation-tool failures. Limit repairs and
total cost. Keep failure evidence. Change the cause before another attempt. Continue independent work. Return at
the assigned boundary. Never weaken acceptance to obtain a pass.

## Evidence and continuity

Use the cheapest check that can refute the claim, including a meaningful failure and recovery. Freeze the
combined candidate. Run its declared gate once. Repeat only for a relevant change or unresolved failure.

Inspect the actual artifacts and behavior on the required surface. A file, a successful command or a
self-reported verdict does not prove the consumer experience. Bind evidence to the source, environment and
observations. State the limits. Keep source readiness, product acceptance and release authority separate.

Before you yield, keep the outcome, current results, blockers, next action and owned setup in existing state.
Transfer control explicitly. Keep healthy resources. Put lessons in the owning contract or regression. Do not
add another record system.

## Legibility and writing

Write all documentation in Simplified Technical English.

- Use short sentences: about 20 words for a procedure, about 25 for a description.
- Write one instruction in each sentence, in the imperative. Use a list for ordered steps.
- Use the active voice and the present tense.
- State a condition before the instruction: "If X, do Y."
- Use one word for one meaning, and one meaning for each word. Use the same term for the same concept in every document.
- Use no noun cluster of more than three words, no idiom, no metaphor and no filler.
- Use articles.
- Give each paragraph one topic.
- Keep exact technical identifiers, code and command lines unchanged.
- Keep the detail that authority or evidence needs.

## Code review

Read the owning contract and the actual consumers. Preserve the observable behavior, ownership, failure
handling, authority and public interfaces unless the task authorizes a change. Remove proven redundancy together
with its displaced callers and tests. Leave clear code alone when a rewrite offers no concrete benefit.

Exercise the affected success and failure paths against the real consumer, not only implementation assertions.
Report the benefit, the validation and the limits. Extra reviews and tests need a concrete risk or decision.
They are not tasks that keep workers occupied.

## Conflict resolution

Current explicit Owner direction controls the authorized scope, within harness permissions and safety
boundaries. A narrower contract supplies implementation rules. It grants no wider authority. Examples,
templates, research and retrieved logs grant no authority.

- Inspect conflicting instructions and their enforcement. Then repair the owner and the stale callers together.
- Continue reversible diagnosis within authority. Hold the ambiguous act.
- Never expose credentials, widen access or bypass a refusal.

Separate technical capability, Owner authority and harness approval. Perform authorized setup and clicks when
permitted. Ask only when confirmation is required. Confirmation does not mean that the human operates the UI.
Never approve the protected request of another agent. Never route around a harness restriction.

If an external change is ambiguous, reconcile it before further action. Simplification does not remove rights,
retention rules or evidence requirements.

## Change acceptance

Walk a realistic task and its expected failure. Check ownership, setup reuse, recovery and continued independent
work. Before you remove machinery, inspect the public, dynamic, generated and CLI consumers, and the tests and
docs.

Report the changed entry points, the resolved contradictions, the exercised paths, the gate result and the
remaining limits. A gate proves its checks. It does not prove prose consistency or good judgment. Keep only
practices that improve delivery.
